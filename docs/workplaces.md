# Multi-service and multi-repo environments

Some development environments are not one app. A platform repository clones several application repositories, runs a reverse proxy and shared infrastructure, and wraps Compose in its own script that generates the root compose file and sets variables. Agents should work across every repository and reach every service the way a developer does, while each repository keeps its own agent instructions.

One sidecar serves such an environment. This page shows how, using this layout as the example:

```text
platform/
├── dev.sh                     # wraps docker compose: sets PLATFORM_ROOT, uses stacks/docker-compose.yml
├── .env                       # per developer (gitignored)
├── .agentic-devbox/           # created by `agentic-devbox init`
├── AGENTS.md                  # instructions for agents working across the platform
└── stacks/
    ├── docker-compose.yml     # generated by dev.sh: includes infrastructure and every app repo
    ├── compose.agents.yml     # the sidecar (this page)
    ├── infrastructure/        # traefik (network aliases api.example.test, ...), mysql, ...
    ├── service/api/           # app repository with its own AGENTS.md and compose file
    └── client/shop/           # app repository
```

## 1. Join the networks instead of one app

There is no single app whose `localhost` the agents should share. Services are addressed by hostname through the proxy, and sharing one app's namespace would tie the sidecar to that app's restarts and its `/etc/hosts`. So the sidecar joins the project's networks as a container of its own. [architecture.md](architecture.md#the-network-model) compares the two modes.

## 2. The compose file

Keep everything agentic-devbox needs in one file next to the root compose file:

```yaml
# stacks/compose.agents.yml
include:
  - path:
      - ${AGENTIC_DEVBOX_HOME:-${HOME}/.config/agentic-devbox}/base-compose.yml
      - ${AGENTIC_DEVBOX_HOME:-${HOME}/.config/agentic-devbox}/exec-bridge.yml
    # The platform root: /workspace, .agentic-devbox/ and its home/ live there, not in stacks/.
    project_directory: ..

services:
  # No network_mode: its own container on the project's default network.
  # Add `networks: [default, backend]` if the services use other networks too.
  universal-agent:
    working_dir: ${PLATFORM_ROOT:?run via ./dev.sh}
    volumes:
      - ${PLATFORM_ROOT}:${PLATFORM_ROOT}            # section 4
    tmpfs:
      - ${PLATFORM_ROOT}/.agentic-devbox:ro,mode=0555  # section 4
```

- `project_directory: ..` is relative to this file, so the blueprint's `./` is the platform root: it is mounted at `/workspace`, and the config layers and logins come from `platform/.agentic-devbox/`.
- Named volumes take the project name as a prefix, so they belong to this environment only.
- Variables such as `AGENTIC_DEVBOX_MEMORY` come from the `.env` of the top-level Compose project. When the script runs `docker compose -f stacks/docker-compose.yml`, that is `stacks/.env`, not `platform/.env`.

## 3. Hostnames and HTTPS

The sidecar resolves what the project's networks offer: service names, and the network aliases a service declares. If the proxy carries `api.example.test` as an alias, `https://api.example.test` in the sidecar reaches the proxy and the proxy routes it, as on your machine. A hostname nobody declares does not resolve to anything useful. That is deliberate: the sidecar follows the access your Compose file grants. To give agents another hostname, add it to the proxy's aliases.

On Docker Desktop, names that Docker's DNS does not know fall through to your machine's resolver. If that resolver answers `*.example.test` with `127.0.0.1` (dnsmasq and similar), the answer points at the sidecar itself.

A proxy with certificates from a private CA (mkcert and similar) needs trust in three places, because each kind of client uses its own store:

| Client | Trust store | Setting |
| --- | --- | --- |
| curl, git, other OpenSSL clients | the system bundle | mount a bundle with the public CAs plus yours over `/etc/ssl/certs/ca-certificates.crt` |
| Node (scripts, MCP servers) | its own list | `NODE_EXTRA_CA_CERTS` with your CA's PEM |
| Chrome | its own (NSS), recreated at every start | `AGENTIC_DEVBOX_BROWSER_IGNORE_CERT_ERRORS: "1"` |

```yaml
  universal-agent:
    volumes:
      - ./infrastructure/certs/ca-bundle.crt:/etc/ssl/certs/ca-certificates.crt:ro
    environment:
      NODE_EXTRA_CA_CERTS: ${PLATFORM_ROOT}/stacks/infrastructure/certs/ca/rootCA.pem
      AGENTIC_DEVBOX_BROWSER_IGNORE_CERT_ERRORS: "1"
```

The mounted bundle replaces the system one, so it must include the public CAs. Ignoring certificate errors applies to every site the sandbox Chrome opens; use it for local development only.

## 4. Keep the host's paths

Platform scripts often write absolute host paths into files agents read, for example a generated note in each repository that says "read `/Users/you/platform/AGENTS.md`". Mounting the platform at its host path as well as at `/workspace` keeps those paths valid, makes paths in agent output match the ones on your machine, and lets the CLI start agents in the matching folder (section 7).

`PLATFORM_ROOT` must be an absolute path that your script exports. Compose has no variable for the project folder.

The `tmpfs` line is required. The blueprint hides `.agentic-devbox` (logins, `secrets.env`, the config layers) only under `/workspace`. Without the extra entry, the second mount shows it read-write, and an agent could edit `settings-project.json` to widen its own permissions at the next restart.

## 5. A script around Compose

Projects that wrap Compose, for example to pass `-f` and set variables guarded with `${VAR:?run via ./dev.sh}`, fail with plain `docker compose`. Tell the CLI to use the script, in the platform's `.env` or your shell:

```bash
AGENTIC_DEVBOX_COMPOSE=./dev.sh compose
```

The CLI runs it from the platform root (the folder with `.agentic-devbox/`). The script must:

- pass its arguments on unchanged: `./dev.sh compose ps -q universal-agent` runs `docker compose ... ps -q universal-agent`;
- print its own messages, such as echoed commands, to stderr: the CLI reads `ps` output from stdout.

`COMPOSE_FILE` in `.env` does not help here: Compose ignores it when the script passes `-f`.

## 6. Opt in when the root compose file is generated

Compose has no optional `include`, and committing a plain include breaks `up` for every teammate without agentic-devbox. When the script generates the root compose file, let it add the include line only for developers who opted in:

```bash
# in the generator, after the other include lines
if [ -f "${AGENTIC_DEVBOX_HOME:-$HOME/.config/agentic-devbox}/base-compose.yml" ] && [ -d "$PLATFORM_ROOT/.agentic-devbox/home" ]; then
  printf '  - path: compose.agents.yml\n'
fi
```

A developer opts in with `agentic-devbox init --network default` in the platform root, which creates `.agentic-devbox/home/`, then regenerates. Turning it on does not recreate the other containers: their configuration is unchanged, so `up` only adds the sidecar and the bridge.

## 7. One agent per repository

Agents read their instructions from the folder they start in and its parents. From your machine:

```bash
cd stacks/service/api
agentic-devbox claude        # starts in .../stacks/service/api inside the sidecar
```

The CLI finds the platform root, runs the agent in the sidecar folder that matches yours, and the agent reads that repository's `AGENTS.md` or `CLAUDE.md` and the platform's above it, as on your machine. All agents in the environment share one login state (`platform/.agentic-devbox/home`). For separate logins per repository, run one sidecar per repository ([shared-app-environments.md](shared-app-environments.md#alternative-one-sidecar-per-project)).

## 8. Tooling in the other containers

With the exec bridge, the platform's own commands work inside the sidecar: `./dev.sh exec api composer test` runs `docker compose -f ... exec api composer test`, the sidecar's `docker` client skips `-f` and forwards the exec. The script's other commands (`up`, `down`, `logs`, `build`) are refused, so agents cannot restart or remove the environment.

If the containers run as root and the tooling expects it, set `AGENTIC_DEVBOX_BRIDGE_USERS: any` on `agent-exec-bridge`. Then check what the containers mount: a proxy that reads the Docker socket (Traefik's Docker provider, for example) lets an agent with root in that container control Docker. See [exec-bridge.md](exec-bridge.md#choose-a-user-policy) and [security.md](security.md#shared-app-containers).
